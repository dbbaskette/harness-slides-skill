# Harness Slides 0.19.0

Saved work is no longer pinned to one installed version, and an update replaces
the previous version instead of keeping it.

The runtime has one address. `start`, `resume`, `cached`, `pin`, `version`,
`doctor` and the installer all return `<shared>/current`, the pointer the
installer moves, and never a folder under `versions/`. A path a caller recorded
keeps working after an update and runs the new code.

A task keeps its instructions, not a runtime. Its pin holds the guidance
revision and file hashes, the version the work started on for information, and
the minimum runtime its guidance declared. `resume` and `cached` return the
runtime installed now and never refuse because the runtime moved, changed or
its old folder is gone. Pins written by earlier versions, which named a version
folder and a hash of every runtime file, resume the same way with no migration.
When the installed version differs from the one the work started on, the result
adds `startedRuntimeVersion` and a one-line `notice`. Resume keeps the saved
guidance and does not fetch; starting a new task is still how existing work
adopts newer guidance. Saved guidance that needs a newer runtime than the one
installed is refused with the usual message to update with the trusted
installer, and a new task on an older runtime still falls back through the
compatibility index.

Project records do not depend on the installed version. An unbranded build
recorded the path of the neutral design defaults inside the version folder, and
every later preview, render and review read that file; it is now named through
the pointer and not read back at all, since the contract carries the whole
design under its revision. Builds made by earlier versions continue without
recompiling. A brand's own sources are checked as before, and the hashes that
protect the scene, images, approvals and rendered deck are unchanged. Section
briefs written by `outline start` name the pointer. Native render bundles stay
keyed by the runtime code: the first preview or review after an update draws
again rather than reusing pixels the previous code drew, and existing previews,
critiques and reviews remain valid.

The installer removes every other folder directly inside its own `versions/`
once the pointer has moved. A folder it cannot remove is reported in
`keptVersions` and does not fail the install; a link inside `versions/` is
neither followed nor removed; nothing is removed when the pointer did not move.
A skill link that pointed into `versions/` is moved to the pointer. A link or
folder at a skill location that leads elsewhere is left as it is and listed in
`skipped`, where the installer used to stop; the other harnesses are still
installed. The result's `runtime` is the pointer and `versionId` names the
folder behind it. `install.mjs` now also runs when reached through the pointer
or a skill link; it used to do nothing there.

Callers that kept the returned `runtime`, resolved a skill link to its target,
or read the installed folder's name from the installer's `runtime` need the
changes listed in the
[integration contract](../specs/2026-10-14-design-integration-contract.md#one-runtime-address-in-0190).
A command already running from the previous version when an update removes it
may fail and can be run again. Capability `stable-runtime` is added. The minimum
runtime for current guidance stays 0.17.0: the guidance asks only that each
session use the runtime its own start or resume returned, which holds on
earlier runtimes too.

This was verified with temporary installations in the test suite, not with an
update of a real installation or a live deck.
